# MiKo_3129: Assertions should not await the actual value

## Cause

The `actual` argument of an `Assert.That` call contains an `await` expression.

## Rule description

Assertions should only compare already-available values.
Awaiting an expression directly inside `Assert.That` mixes the asynchronous operation with the assertion itself, which makes the code harder to read and follow.

### Rationale behind

A test usually has clear steps:
1. Arrange
2. Act
3. Assert

Awaiting a value directly inside an assertion mixes the _Act_ step and the _Assert_ step into a single line.
This makes the test harder to follow, because obtaining the result and checking the result become one combined action.

Separating these steps provides several important benefits:

- **Clearer structure**:
  The test clearly shows an act step, where the result is obtained, and a separate assert step, where the result is checked.
  This structure is easier to recognize and follow.

- **Easier debugging**:
  When the awaited call fails, the failure happens on its own line.
  This makes it easy to see that the problem occurred while getting the result, not while checking it.

- **Better readability**:
  The assertion line stays short and focused on the check itself.
  A reader does not need to untangle an asynchronous call from the comparison logic.

- **Consistent test style**:
  All results are obtained in the same way, then stored in a variable, then checked.
  This creates a predictable pattern that is easy to follow across the whole test suite.

## How to fix violations

To fix a violation of this rule, await the expression first and store its result in a local variable.
Then pass that variable to the assertion instead of the awaited expression.

## How to suppress violations

```csharp
#pragma warning disable MiKo_3129
#pragma warning restore MiKo_3129
```
