# MiKo_0008: Avoid types with too many namespace dependencies

## Cause

A file contains a large number of using directives.

## Rule description

A large number of using directives often means that a type depends on many different parts of the system.
Such a type is often too complex, tightly coupled, and harder to understand, maintain, and reuse.
Consider reviewing the design and splitting responsibilities if necessary.

### Rationale behind

A high number of using directives often indicates that a type depends on many different namespaces.
Such dependencies make the type harder to read, harder to maintain, and harder to reuse.

There is no fixed limit for the number of using directives.
The acceptable number depends on the responsibility of the type:

- **0 to 15 usings**:
  Usually normal for small, focused types.
  Easy to understand and shows limited dependencies.

- **More than 15 usings**:
  A warning signal.
  Often indicates too many responsibilities.
  High chance of a "god type" or poor design.

The exact number of using directives is not the real problem.
The number of dependencies behind those using directives is the real problem.

Keeping the number of using directives low provides several important benefits:

- **Fewer dependencies**:
  A type with few using directives relies on fewer external APIs.
  Fewer concepts need to be understood at once, which makes the code easier to read.

- **Clear responsibility**:
  A type with many using directives often does too many things.
  It mixes different responsibilities and violates the Single Responsibility Principle.
  A type with fewer using directives usually has a clearer, more focused responsibility.

- **Lower coupling**:
  A type with many using directives is often tightly connected to many other parts of the system.
  Changes in other namespaces can affect such a type.
  Lower coupling makes reuse easier, as fewer dependencies are required.

- **Better maintainability**:
  A file with fewer using directives is easier to maintain.
  Refactoring becomes less complex and less risky.
  Bugs are easier to analyze and fix.

- **Improved readability**:
  A long list of using directives adds noise at the top of a file.
  Important dependencies are harder to spot in a long list.
  A short list keeps the intent of the type clear.

- **Better design**:
  A type with many using directives may need to be split into smaller types.
  A well-designed type usually needs only a few namespaces.
  A better design reduces the number of dependencies.

## How to fix violations

To fix a violation of this rule, review the type and identify its different responsibilities.
Split the type into smaller types so each type has a single, focused responsibility.

## How to suppress violations

```csharp
#pragma warning disable MiKo_0008
#pragma warning restore MiKo_0008
```
