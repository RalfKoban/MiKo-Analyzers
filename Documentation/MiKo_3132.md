# MiKo_3132: Do not assert `NullReferenceException` in unit tests

## Cause

A unit test asserts that a `NullReferenceException` is thrown.

## Rule description

Tests should not assert for `NullReferenceException`, as it indicates a bug in the code under test and not an intended behavior.
Instead, they should assert for a specific exception or fix the code.
This makes the tests more meaningful and easier to maintain.

## Rationale behind

A `NullReferenceException` signals a programming error.
It is thrown when code accesses something that is `null`, usually because a check for `null` is missing.
Code that checks for `null` and then throws this exception on its own uses the wrong exception, because it does not tell the caller what went wrong.

A test that expects this exception treats the bug as expected behavior.

Not asserting this exception provides several important benefits:

- **Tests Describe Intended Behavior**:
  Tests should show what the code is supposed to do.
  A `NullReferenceException` is never an intended result, so asserting it gives a wrong picture of the code.

- **Bugs Are Not Hidden**:
  A test that expects the exception passes as long as the bug exists.
  The passing test makes the code look correct, but it is not.

- **Bug Fixes Do Not Break Tests**:
  A test that expects the exception fails as soon as the missing check is added, although the code became better.
  Such a failure is confusing and costs time, because the developer has to find out that the test is wrong and not the fix.

- **More Meaningful Tests**:
  Tests that assert a specific exception show what the code promises to do.
  Other developers can see directly what the expected behavior is.

## How to fix violations

To fix a violation of this rule, first find out why the exception is thrown.
The stack trace of the exception shows where it is thrown, either in the test, in the code of the project, or in a library.

In most cases, the exception is caused by a bug in the code under test.
Then two things have to be done.
The code under test has to be fixed, so that it does not throw a `NullReferenceException` anymore.
The assertion of the `NullReferenceException` in the test has to be removed or replaced by an assertion of the new, expected behavior, such as an `ArgumentNullException`.

The correct fix depends on the reason:

- **Missing setup in the test**:
  The exception may be caused by the test itself.
  For example, a field is not initialized or a mock or stub is not set up.
  In such a case, only the test has to be fixed.
  The setup should be completed, so that the test runs the code under test and not a mistake in the test.

- **Missing argument check**:
  A method may have no check for an argument that is `null`.
  In such a case, the developer should add the check to the method.
  The test should then assert an `ArgumentNullException`.

- **Wrong exception thrown on purpose**:
  The code may check for `null` and then throw a `NullReferenceException` on its own.
  In such a case, the exception type is wrong and should be replaced.
  If the `null` value is an argument, the code should throw an `ArgumentNullException`.
  If the `null` value comes from somewhere else in the code, the code should either handle the missing value or throw a meaningful exception.
  A good choice is an `InvalidOperationException` or a similar one.

- **Third-party library or framework**:
  The exception may be thrown inside a third-party library or the framework.
  The library cannot be changed, and the test should not verify the exception.
  Such a test checks the behavior of the library and not the code of the project.
  Instead, the call should be placed inside the project's own code.
  That code should handle the missing value or report it with a meaningful exception, and the test should assert that behavior.

- **Test documents current behavior**:
  A test may assert the exception only to document the current behavior.
  In such a case, the code under test should be fixed, and the test should be changed to assert the expected behavior.
  If the test has no value without the exception, the developer should remove it.
  If such a test fails after a bug was fixed, the fix is not the problem.
  The bug was in the code, and the test only recorded it as expected behavior.

## How to suppress violations

```csharp
#pragma warning disable MiKo_3132
#pragma warning restore MiKo_3132
```
