# MiKo_3239: Avoid boolean parameters in attribute constructors

## Cause

An attribute constructor accepts one or more bool parameters.

## Rule description

Attribute constructors should not accept bool parameters as they do not tell the reader what they mean at the call site.
Expose them as named properties instead, so the intent is clear where the attribute is used.

## Rationale behind

A bool value at a call site does not explain what it stands for.
A reader sees only `true` or `false` and has no clue what behavior is switched on or off.
This makes attribute usages hard to understand without jumping to the constructor definition.

Avoiding bool parameters in attribute constructors provides several important benefits:

- **Clearer Call Sites**:
  A named property shows its meaning directly where the attribute is applied.
  There is no need to look up the constructor to understand what a value does.

- **Reduced Ambiguity**:
  When an attribute has several bool parameters, it is easy to mix up their order or meaning.
  Named properties remove that risk because each value is assigned explicitly.

- **Easier Maintenance**:
  Properties can be added or reordered without breaking existing attribute usages.
  Constructor parameters, on the other hand, are tied to a fixed position and type.

- **Better Discoverability**:
  Named properties show up with helpful names in code completion.
  This makes it easier to find and use the correct setting.

## How to fix violations

To fix a violation of this rule, remove the bool parameter from the constructor and expose it as a named property with a default value instead.
Consumers of the attribute can then set the property explicitly by name.

## How to suppress violations

```csharp
#pragma warning disable MiKo_3239
#pragma warning restore MiKo_3239
```
