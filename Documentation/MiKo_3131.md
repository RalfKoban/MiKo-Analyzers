# MiKo_3131: Do not use mocks in production code

## Cause

Production code uses mock types from a mocking framework, such as Moq, NSubstitute, or Rhino Mocks.

## Rule description

Mocks are intended for unit tests and test code.
They help simulate dependencies during testing.
Do not use mock types from frameworks such as Moq or NSubstitute in production code.
Production code should work with real implementations or abstractions, not test doubles.

Using mocks in production code can hide design problems and make the code harder to understand and maintain.

## Rationale behind

Mocking frameworks are made to replace real dependencies in tests.
They allow tests to run in isolation and to check how code behaves.
They are not made to run inside a shipped application.

When production code uses mocks, the application may behave differently than expected.
A mock only returns what it was told to return.
It does not contain the real logic.
This can hide missing features or design problems.

Mocking frameworks are also test dependencies.
If production code references them, they have to be shipped with the application.
This increases its size and creates unneeded dependencies.

Not using mocks in production code provides several important benefits:

- **Reliable Behavior**:
  Production code runs with real implementations.
  The application does what it is supposed to do and not what a mock was told to do.

- **Clear Separation**:
  Test code and production code stay separate.
  It is easy to see which code is shipped and which code only exists for testing.

- **Fewer Dependencies**:
  The application does not need to reference mocking frameworks.
  This keeps the deployment smaller and reduces the risk of version conflicts.

- **Better Design**:
  If a mock seems to be needed in production code, the design often has a problem.
  Fixing the design leads to code that is easier to understand and maintain.

- **Improved Stability**:
  Mocks create types at runtime and can behave in unexpected ways.
  Avoiding them in production code removes this source of surprises.

## How to fix violations

To fix a violation of this rule, remove the usage of the mocking framework from the production code.
Use real implementations or abstractions instead.

Move any code that needs mocks into the test projects.

## How to suppress violations

```csharp
#pragma warning disable MiKo_3131
#pragma warning restore MiKo_3131
```
