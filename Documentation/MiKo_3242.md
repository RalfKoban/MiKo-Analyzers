# MiKo_3242: Avoid race conditions when raising events

## Cause

An event is checked for `null` in one statement and invoked in a separate statement.

## Rule description

Checking an event for `null` and invoking it in a separate statement can cause a race condition if another thread unsubscribes the last event handler between the check and the invocation.
Raise events via `?.Invoke(...)` to make the code thread-safe and more concise.

## Rationale behind

Events are often used in code that runs on multiple threads.
Another thread can remove the last event handler after the `null` check was done, but before the event is invoked.
In that case, the event is `null` at the time of the invocation, and a `NullReferenceException` is thrown.

Such errors happen only now and then and depend on timing.
That makes them hard to find, hard to reproduce, and hard to debug.

The null-conditional operator `?.` reads the event only once.
The check and the invocation work on the same value, so no other thread can change it in between.

Raising events via `?.Invoke(...)` provides several important benefits:

- **Thread Safety**:
  The event is read only once, so there is no gap between the check and the call.
  A handler that is removed by another thread cannot cause a `NullReferenceException`.

- **Fewer Hard-to-Find Bugs**:
  Race conditions occur only rarely and are difficult to reproduce.
  Avoiding them in the first place saves a lot of time that would otherwise be spent on debugging.

- **Shorter Code**:
  One statement replaces the `null` check and the invocation.
  Less code means less to read and less to maintain.

- **Clearer Intent**:
  The `?.Invoke(...)` pattern is well known and shows right away that the event is raised only if there are handlers.

## How to fix violations

To fix a violation of this rule, raise the event via `?.Invoke(...)` and remove the separate `null` check.

## How to suppress violations

```csharp
#pragma warning disable MiKo_3242
#pragma warning restore MiKo_3242
```
